### 落地的契约（后续改动别破坏）

- **`utils/retry.ts`**
  - `DEFAULT_RETRY_DELAY_MS = 2000`（替换 `withRetry` 第 4 参的字面量，避免第二处 `2000` 漂移）。
  - **`retryBudgetMs(perAttemptMs, retries, delayMs)`**：第一个参数是**"单次尝试的最坏墙钟时长"**，
    **不是名义 `timeout`**。调用方漏算宽限，这个"上界"就不成立，外层会抢跑甚至赢过最后一次尝试。
  - `withRetry` 增加**第 6 个可选参数** `shouldRetry?: (error, attempt) => boolean`。**不传 = 旧行为逐字不变**；
    返回 false → **立即 throw**，不退避、不调 `onRetry`。
- **`utils/errors.ts`（新）**：`PermanentError`（**显式设置 `name`**——否则按 `err.name` 分类的地方读到 `"Error"`）
  + `isPermanent()`。**只标两处**：spawn 失败（`child.on("error")`，ENOENT/EACCES）、
  `loadSession=false`（能力不匹配）。其余（超时、`connectionError`、非零退出）**保持可重试**。
  **错误消息逐字不变**——`AgentResult.error` 取 `err.message`，这是结果契约。
- **C10 分层语义（唯一真缺陷，已修）**：
  - 外层 `withTimeout` = **整个 agent 的兜底** = `retryBudgetMs(timeout + KILL_ESCALATION_MS, retries)`；
    内层 `AcpRuntime` timer = **单次 execute** = `timeout`。
  - **`KILL_ESCALATION_MS`（3000）必须计入**：reject 落在 `child.on("close")`，子进程若忽略 SIGTERM
    要等 SIGKILL 宽限才被回收，故**单次尝试最坏 = `timeout + 3000`**。漏算的后果不只是错误文案变化：
    前 `retries` 次各耗 `timeout+3000` 时，最后一次**本可成功**的尝试会少拿 `retries × 3000`，**被外层杀掉**。
  - `retries: 0` 时外层 = `timeout + 3000`（**不再等于** `timeout`），默认 600s 下多等 3s = 0.5%，可接受。
- **导出面**：`KILL_ESCALATION_MS` 从 `AcpRuntime` 导出并经 `runtime/index.ts` re-export，但
  **`src/index.ts` 仍是显式命名导出 `{ AcpRuntime, runtimeRegistry }` → 未泄漏到公共 API**
  （`dist/index.d.ts` 0 命中）。
- **`resolveArgs`（已发布导出，签名未变）**：显式 `args` → `agent.command ?? config.defaults.command` 的
  catalog args → provider 的 args。**command 决定自己的 args**，catalog 外的自定义二进制不再被塞 `["acp"]`。
  既有 3 条断言（claude→`[]`、opencode→`["acp"]`、unknown→`undefined`）逐字未动。
- **`configuredAgents()`**：`a.dependsOn ? { ...a, dependsOn: [...a.dependsOn] } : { ...a }` ——
  **不新增键**（写成 `dependsOn: ... : undefined` 会给原本无该键的对象发明一个键）。

### C7 的结论：原评审前提被证伪，**回退为纯注释**

原评审称 `discoveredModels` 缓存"跨 provider / 跨版本不失效、同一 command 名可能指向不同二进制"。
**两条都不成立**：键就是 `command`，跨 provider 天然分开；跨版本要重启进程，重启即清空模块级缓存。
且 `resolveExecutable`（`providers/bridge.ts:69`）是 **command + PATH + 文件系统的纯函数**，
而 `exe = resolveExecutable(command) ?? command`（`AcpRuntime.ts:272`）在**每个分支**上都是 `command`
的 1:1 函数（在 PATH 上原样返回裸名；自带 bridge 返回一一对应的绝对路径；解析不到 `null ?? command`
又回到 command）→ **换键没有任何可观测差异，也就不可能有能区分二者的测试**。
工程师一度写的注释还声称"两种写法（名字与绝对路径）共享一条缓存"——**这是假的**：
`resolveExecutable("/usr/local/bin/opencode")` 在 `resolvesOnPath` 与 `resolveBridgeBinary` 两处都返回 null
→ `?? command` → 键就是那个绝对路径串，与裸名是两个键。**已删。**

**已知限制（照实记录、不修）**：缓存来自某一次 `session/new` 的 `configOptions`，之后该二进制的每个会话都复用。
若某 provider 的广告列表**随会话变化**（账号/订阅），列表会过时；而校验在"模型不在列表里"时
**只发一条 `warn(...)` 并跳过 `setConfigOption`** → **用户配置的模型不生效**。没有真机无法验证。
