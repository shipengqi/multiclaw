## 交互式 CLI 设计讨论(仅设计,未落地代码)

- 需求:`multiclaw` 裸命令 → 交互式终端(像常见 AI agent),但 multiclaw 是「agent 团队」。
- 澄清两种「交互式」:**A 输入式 REPL**(一次会话多轮输入,每轮跑一条 pipeline)/ **B 运行时可干预**(暂停/审批/插话/改向)。结论:先 A 后 B,B 才是团队相对单 agent 的差异化。
- 现状接缝(读码结论):
  - `EventBus` 是**唯一观察缝** → TUI 只是又一个 subscriber,与 `ConsoleReporter`/dashboard 平级(红利:不必改编排层就能接入)。
  - **缺输入缝**:`Orchestrator.run()` 无参、无 `AbortSignal`;config 在 `new Orchestrator()` 时冻结;`cli/commands/run.ts` 结尾直接 `process.exit()`(库路径不该杀进程)。
  - `ClaudeRuntime` 是 `claude -p <prompt>` 一次性子进程,**无 resume/session** → 「运行中插话」必须先升级 runtime 能力(建议加 `capabilities:{resume,interactive}` 能力位,便于降级)。
  - dashboard 的 `useOrchestrationStore` reducer 是纯事件→状态函数,**应上提到 core**(`reduceEvent`)供 dashboard 与 TUI 共用,避免两份逻辑漂移。
  - 并发渲染坑:`agent:output` 是 N 路交织 chunk,须按 agentId demux(已做);但 dashboard 现在是**无限 append** 日志,缓冲区必须封顶(ring buffer)。
- 推荐架构:新增 `packages/tui`(Ink/React for CLI,复用同一 reducer);core 新增 `Session`/`SessionController`(持有 config+workDir+history,`runTurn(input)`);`multiclaw` 裸命令 = 交互,`multiclaw run` = headless 保留。
- 交互模型:turn-based「conductor loop」+ **stage 边界 gate**(审批/改向/补人),leader 作为前台。

### 设计原则:「对齐用户习惯」

每个决定都能追到一个既有约定,不是自创:底部锚定输入框(Claude Code / Codex / aider / gh)、header/body/footer 三段壳(lazygit / k9s / htop)、`──▸` + ①②③ 流水线(cargo / turbo / GitHub Actions)、左 roster 右 stream 分栏(lazygit panes)、状态**字形 + 颜色双编码**(色盲可用 + 复制粘贴后仍可读)、右对齐暗色耗时列(pnpm / cargo)、随上下文变化的提示条(htop F 键)、`?` 帮助与 `/` 命令(Claude Code / Slack / Notion)、滚到底自动恢复 follow(less)。

- **核心约束:提示符永远持有焦点** → 裸键必须让位于打字。**因此只有两个裸键,且都以「输入行为空」为门槛**:`?`(帮助)、`/`(命令面板)。这是整套 keymap 的地基。
- `ctrl+c` **逐层剥离**,绝不在用户没预期时退出:帮助开着→关帮助;有运行中 turn→取消;有输入→清空;都空→退出。`ctrl+d` 空行退出。

### 三个可复用的坑(重要)

### 修:光标闪烁把占位符挤来挤去(用户截图反馈)

现象:空行时光标块闪烁,占位符 `describe what the team should do…` 每秒被推/拉一列。

根因(`components/prompt.tsx` 旧代码):空行分支写的是
```tsx
{caretVisible ? <Text inverse> </Text> : null}
<Text dimColor>{placeholder}</Text>
```
光标是**额外插入的一格**,熄灭时渲染 `null` → 占位符整体左移一列。实测旧结构 dump 出来正是
`"›  describe…"`(两个空格)/ `"› describe…"`(一个空格)。

修法:**光标格恒占一列,且空行时「画在」占位符首字符上**(真终端的块光标就是这样,而不是插在前面)。
```tsx
const ghost = value === ""
const cell  = ghost ? placeholder.slice(0, 1) : value.slice(cursor, cursor + 1)
const tail  = ghost ? placeholder.slice(1)    : value.slice(cursor + 1)
const faded = disabled || ghost
```
两个容易踩的细节:
- **光标必须是兄弟节点,不能嵌套在 dim 的 `<Text>` 里**。Ink 向下合并样式且**无法 un-inherit**(传 `dimColor={false}` 与不传无法区分),嵌套会让反色块跟着变暗、糊掉。第一版写成嵌套,dump 出 `\u001b[2m\u001b[7md`;改成兄弟节点后是 `\u001b[7md\u001b[27m\u001b[2mescribe…`。
- **光标熄灭时的亮度要跟邻居一致**:ghost 上要 dim、已输入文本上要正常,否则那一格会闪亮度。所以用 `dimColor={caretVisible ? disabled : faded}`。
- 附带:`head || " "` 让「光标在行尾」时也恒占一格(旧代码在行尾 `at === ""` 时同样会 0/1 格抖动)。

**Ink 会 trim 行尾的未着色空白** → 行尾那一格在熄灭时会消失(反色时保留)。这没问题:行尾之后没有任何字符会被挤动,真终端光标也是这个行为。测试里用 `trimEnd()` 比较即可。

回归测试(`components.test.tsx` 新增 `describe("Prompt")` 6 例 + `App.test.tsx` 1 例):
- 核心不变量:**两个闪烁相位 stripAnsi 后必须完全相同**(空行、行中、行尾三种)。
- `\u001b[7md`(画在首字符上)、`\u001b[7md\u001b[27m\u001b[2m`(块未被 dim)、`not.toContain("\u001b[2m\u001b[7m")`(没嵌套)。
- `App.test.tsx` 断言整行 `› describe what the team should do…`(恰好一个空格)。
- 已验证**这些测试对旧结构真的会失败**:临时复刻旧结构 dump 出 `"›  describe…"` vs `"› describe…"`,`on !== off` → 测试有真实判别力,不是空过。

### 视觉验证阶段又发现并修掉三个真 bug(靠「渲染真实帧」找出来的)

## TUI 功能讨论:核出来的四个事实(未改动代码,仅调研)

用户提了五个设计问题(团队来源 / 输入 hello / 运行中输入 / 新任务 / 并发)。逐条去代码里核对,发现**两个是 bug、一个是架构前提**:

1. **leader 只能做减法,不能加人。** `Orchestrator.resolveAgents()`(packages/core/src/orchestrator/Orchestrator.ts:133)拿到 `{"run":[...]}` 后执行 `this.config.agents.filter(a => runSet.has(a.id))` —— 结果永远是配置的**子集**。leader 的 prompt 也写明 "Agent IDs must come from the Available Agents list above",契约是封闭的。
2. **幻觉 id → 静默的「成功空跑」(bug)。** 若 leader 报一个配置里不存在的 id,`filter` 得空数组 → `stages = []` → 循环零次 → `allSuccess` 保持 `true` → 照样发 `orchestration:complete { success: true }`。控制台显示 `✓ done`,0 个 agent 跑过,用户看不出。**空计划必须显式报错。**
3. **运行中打字被直接丢弃(bug)。** `App.tsx` 的 `handleKey` 在字符插入前有 `if (running) return`(约 422 行);Prompt 在 running 时 `disabled` 且以 `state.requirement` 为值、关光标。运行中只有 ctrl+c / tab / 方向键 / ctrl+l 有效。
   - 硬约束:`ClaudeRuntime` 是冷启动一次性 `claude -p` 子进程,**无 session 可 resume、无 stdin 通道** → 「运行中注入一句话」在 runtime 层做不到。任何设计只能先做「排队 / 改道」。
4. **每一轮的工作目录都是新的(架构前提)。** `App.startTurn` 里 `runDir = path.join(config.workDir, ".multiclaw", "runs", "run-<stamp>")`,`Orchestrator` 把它一路传给 `AgentRunner` 当作 runtime 的 `workDir`(= agent 的 cwd)。所以**第二轮看不见第一轮写的文件**。`examples/dev-team` 的 `workDir: "./workspace"` 实际 cwd 是 `workspace/.multiclaw/runs/run-<ts>/`(嵌套空目录)。
   - 对 `multiclaw run`(批处理/可复现/隔离日志)是对的;对**交互式控制台**是错的 —— 用户期待「任务一搭好 API,任务二加鉴权」。
   - 另外 `turn:start`(state.ts:346)返回全新 state(agents 重新 seed、stages 清空、scroll 归零)→ **上一轮日志全丢**,没有历史。

**结论(给用户的建议)**:Q3/Q4/Q5 都要求「同时存在多个轮次」,而 `TuiState` 今天只描述一轮。建议先把状态单位从「一轮」换成「一个任务」(`tasks: TaskState[]` + `activeId` + `queue`),一次重构同时解决队列/历史/并发,避免 `state.ts` 被重写三遍。注意 `orchestration:start` 分支已经能对 roster 外的 agent `blankAgent` 新建,所以状态层比想象中更接近目标。
- 推进顺序建议:修两个 bug → 意图路由(reply/ask/run 三态,leader 当路由器)→ TaskState 重构 → 队列 → 历史+工作区 → 并发。
- 相关 smell:`Orchestrator.run` 里 `i === 0 && stage.some(a => a.id === "architect")` 把 agent id 硬编码了,改名后 task-plan 就不再生效。

## 本轮实现(两个缺陷修复)

### 1. core:leader 空计划不再静默成功

- `resolveAgents` 里 leader 报的 id 不在配置中时,原来**静默丢弃**。现在逐个发 `orchestration:warning`(`The leader named "X", which is not in the config — ignoring it.`)。

- 措辞区分两种空:`usedLeader ? "…none of the configured agents…" : "The config lists no agents…"`。
- 测试 3 例(空计划失败 + 未知 id 告警但仍跑已知的 + 配置本身无 agent 时不甩锅给 leader)。

### 2. TUI:运行中输入改为排队

## Q2 实现:leader 三态意图路由(reply / ask / run)

**契约**(`packages/core/src/types/leader.ts` 新增 `LeaderMode` / `LeaderDecision` / `LeaderMessage`):

```json
{"mode": "run",   "run": ["agent-id", ...]}
{"mode": "reply", "message": "..."}
{"mode": "ask",   "message": "..."}
```

- **解析器**独立成 `packages/core/src/utils/leaderDecision.ts` 的 `parseLeaderDecision(text)`(纯函数,单测 10 例)。逐个数 `extractJsonObjects` 的结果,取第一个「读得通」的:
  - `mode` 缺失但有 `run: string[]` → 仍然当作 run(**向后兼容**:`mode` 字段是后加的,模型漏写时计划仍应生效)。
  - `reply`/`ask` 的 `message` 为空串 → 不算数,继续往后找。
  - `mode` 是别的值 → 不算数。
- **`Orchestrator.resolveAgents` → `resolveTurn`**,返回判别联合 `Resolution = {kind:"run"; agents} | {kind:"message"; mode; message}`;原来直接返回 `AgentDefinition[]` 的那套逻辑拆成 `selectAgents(run)`(子集裁剪 + 未知 id 告警 + `agent:skipped` + `dependsOn` 剪枝)。
- **关键反转**:leader 输出里**没有**任何可解析 JSON 时,原来 `return this.config.agents`(跑全队);现在把它的散文当作回答 → `{kind:"message", mode:"reply"}`。这就是「输入 hello 不再烧掉整支团队」。
  - 例外:leader 输出**全空白** → 视作 leader 失败(见下)。
- **leader 失败 / 无输出** → warning + 回退跑完整配置团队。理由:leader 是基础设施,不是任务本身;需求本身可能仍然完全可执行。原来这条路径**完全静默**,现在有 `The leader could not be reached — running the full configured team.`。
- **新字段 `OrchestratorResult.reply?: LeaderMessage`**(不是新事件类型!)。理由:仓库既有约定就是「事件载荷 = result」(`orchestration:complete` 的 payload 类型就是 `OrchestratorResult`),所以回答挂在 result 上,`orchestration:complete` 一次性带出来。**没有新增 `orchestration:message` 事件。**
  - `success: true` 且 `agentResults: []` 本来无法区分「团队跑完了」和「没人跑」;`reply` 就是那个判别位。
- `finishWithMessage(mode, message, startTime)`:发 `orchestration:complete`(带 reply),**不发 `orchestration:start`**(没有 pipeline,发 start 会让 UI 画出并不存在的 stage)。
- **leader prompt 重写**(`packages/core/src/agents/leader.ts`):三态契约写进 SYSTEM 与 TASK。`description` 从 `scopes the pipeline` 改成 **`routes the request`**(它现在也负责 reply/ask)。
- **CLI 非 TTY 路径**(`ConsoleReporter`):`orchestration:complete` 里有 `reply` 时先打印回答,标题改为 `✓ Answered` / `⚠ Needs your input`,不再谎称 `All done`。

### TUI 侧

- `TuiState.reply?: LeaderMessage`,由 `orchestration:complete` 写入,`turn:start` 清空(旧回答留着会被误读成对新需求的响应)。
- 新组件 **`ReplyPanel`**(`components/panels.tsx`):**接管 body**(与 `WelcomePanel` 同一套路数)——没有 pipeline 可看,文字就是全部结果,分给两个无事可做的面板只会挤小唯一值得读的东西。`ask` 用 `?` + warn 色 + `the team needs a decision` + `Answer below and press enter.`;`reply` 用 `◆` + accent + `answered`。正文用**单个 `<Text>`** 让 Ink 自己折行(拆成多行数组会引入 index key,且截断更早)。
- 状态行:`✓ answered` / `? needs your input`(**不能写 done** —— 那是在声称一件没发生的事)。
- **提示栏在 reply 面板出现时不再提 `tab`**:面板不读 `focusId`,继续写 `tab switch` 就是重演「tab 坏了」。改成 `enter sends · / commands · ? help`。
- 新增 `GLYPH.ask = "?"`。

## Q4 实现:持久工作区 + 可回看的历史

### 1. 控制台的每一轮共用同一个 `workDir`

`App.startTurn` 原来构造 `runConfig = {..., workDir: runDir}`(`runDir = <workDir>/.multiclaw/runs/run-<stamp>`),而 `Orchestrator` 把它当 agent 的 cwd → **第二轮看不见第一轮写的文件**。现在:

```ts
const logDir = path.join(config.workDir, ".multiclaw", "runs", `run-${stamp}`, "logs")
const runConfig = { ...config, context: { ...config.context, requirement }, logDir }  // 不再覆盖 workDir
```

- 只有日志按轮隔离。运行目录是「发生过什么」的记录,不是干活的地方。
- **`multiclaw run` 保持沙箱化**(每次调用一个 `run-<stamp>/`):批处理要可复现,控制台要迭代。这是有意的不对称,已在 README 说明。
- **连带必须修的坑**:`applyTaskPlan` 从 `workDir/task-plan.json` 读计划,而工作区现在跨轮存活 → 若某轮 architect 没写新计划,会把**上一轮的计划**套到新需求上。修法:新增 `Orchestrator.clearStaleTaskPlan()`,在 `run()` 开头 `fs.rmSync(path.join(this.workDir, "task-plan.json"), { force: true })`。
  - 连带:`Orchestrator.run.test.ts` 里三例原本在 `run()` **之前**就把 task-plan.json 写好;现在必须改成「architect 跑的时候写」,否则会被新逻辑清掉。改完反而更贴近真实。

### 2. 历史:把「一轮」从「控制台」里拆出来

**`TurnView` / `TuiState` 拆分**(`state.ts`)——这是历史的使能重构:

```ts
interface TurnView { turn; requirement; phase; startedAt; endedAt; stages; agents;
                     leaderIds; focusId; autoFollow; scroll; success; totalDuration; warning; reply }
interface TuiState extends TurnView { name: string; history: TurnView[]; view?: TurnView }
```

- 好处:**既有测试几乎全绿**(`state.agents` / `state.focusId` / `state.turn` 这些访问路径不变),因为 `TuiState` 仍然**就是**一个 TurnView。
- 所有只读辅助函数(`progress` / `turnElapsed` / `visibleLog` / `stageStatus`)的参数类型从 `TuiState` 放宽到 `TurnView`;所有面板组件的 prop 从 `state` 改名成 **`turn`**(它可能是一轮过去,叫 `state` 是误导)——连带 `components.test.tsx` 里 17 处 `state={...}`。
- `history` 只存**被更新的一轮顶替掉的**轮次(在 `turn:start` 里 push)。**当前屏幕上的那一轮不进 history** —— 它已经在用户眼前,列出来等于提供「给你看正在看的东西」。`turn === 0`(种子 roster)不记录。
- `MAX_HISTORY = 20`,`.slice(-MAX_HISTORY)`。
- `snapshot(state)` **逐字段写出**而不是 `...state` 展开:展开会把 `history` 拷进自己,形成平方级内存。
- **`mapShown(state, fn)`**:`focus:cycle` / `focus:set` / `stream:scroll` / `stream:clear` 都过它。有 `view` 时改动落到 `view`(**detached copy**),否则落到 live turn。
  - 两个不变量:① 回看**不能**动正在跑的轮次的焦点/滚动;② 回看也**不能**改写 history 记录本身(所以记录永远干净,重新打开还是停在尾部)。
  - `fn` 返回同一对象 = 无变化 → 返回原 state,保住 reducer 的 `toBe` 恒等契约(既有 no-op 测试依赖它)。
- 新 action:`view:open`(按 turn 号在 history 里查,查不到就 no-op)/ `view:close`。
- `turn:start` 同时清 `view`(新一轮开始,面板属于这一轮)。

### 3. 历史 UI

- **`HistoryOverlay`**(`components/overlays.tsx`):**最新在最上面**;每轮**两行**(第一行 `› turn N · ✓ done · 4.2s · 2/2 agents`,第二行缩进的需求原文)——挤成一行会把唯一能识别这一轮的字段截掉。头部沿用 TeamPanel 的 `space-between` 惯例(`HISTORY … N earlier`)。
  - `outcome(turn)`:reply → `✓ answered` / `? needs input`;`phase !== "complete"` → `interrupted`;否则 `✓ done` / `✗ failed`。
- `/history` 命令(`commands.ts` 里 availability `always`)。空历史时只给 notice,不开浮层。
- 浮层是**模态**的:`handleKey` 里排在 `helpOpen` 之后、`menuOpen` 之前,`↑↓` 选择、`enter` 打开、`esc` 关闭,其余按键吞掉(否则方向键会滚到它背后的面板)。
- `layout.ts`:`LayoutInput.helpOpen` **改名成 `overlay`**(现在两个模态共用),新增 `viewing?: boolean` → 多留一行给 `viewing turn N · <需求> · esc to return` 横幅。`Layout.welcome` 与 `showRail` 都按 `!overlay` 算。
- `esc` 优先级:**先退出回看**(有 `view` 时),否则清空输入行。提示栏在回看时显示 `esc live · tab agent · ? help`。
- 渲染统一走 `const shown = state.view ?? state`,`PipelineRail` / `TeamPanel` / `StreamPanel` / `ReplyPanel` 全部拿 `shown`,`hasRail` 也按 `shown` 算。
