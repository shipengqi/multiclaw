## 发布流程改为「一键手动发布」(方案 A,已落地)

- 背景:用户反馈 changesets 的自动发布「变复杂了、不好控制」——本质不是步数变多,而是控制权从人转移到了状态机(任何 push 到 main 都是潜在发布事件)。四个候选中选了 A。
- `.github/workflows/release.yml` 触发从 `push: main` 改为**仅 `workflow_dispatch`**。合并 PR 不再触发任何发布。
- 步骤:checkout(`ref: main` + `fetch-depth: 0`,后者是 CHANGELOG 关联 commit 所必需)→ install → 校验有待发布 changeset(否则 `::error::` 直接失败)→ `pnpm -r build` → `pnpm version-packages` → 提交并推送 `chore: release` 到 main → 有 `NPM_TOKEN` 时写 `~/.npmrc` → `pnpm release` → `git push origin --tags`。
- 新增 `dry_run` 布尔输入:只 build + version 并打印 `git diff --stat`,不提交/不推送/不发布。
- **移除 `changesets/action`**(它是 PR 模型)。副作用:不再自动创建 GitHub Release,只创建并推送 git tag;已在文档「补充说明」里给出补 `gh release create` 的做法。
- 写文档前做的源码级验证(避免凭记忆写错):
  - `changeset publish` 只创建**本地** tag,不推送(`@changesets/cli/dist/usingCtx.mjs` 的 `createGitTags` 只调 `git.tag`)→ 所以必须补一步 `git push --tags`。
  - 无新版本可发时 `changeset publish` 是空操作(exit 0);有包发布失败时 `ExitError(1)`。
  - `changeset version` 在无待发布 changeset 时 `ExitError(1)`(`dist/version.mjs`)→ workflow 因此加了前置检查。
  - `format: "auto"` 会检测到 Biome(根有 `biome.json` + `@biomejs/biome`),但 Biome **忽略 .md**(实测 `Formatted 0 files` / `No files were processed`,exit 0),所以不影响 CHANGELOG 生成,未改 `.changeset/config.json`。
- 运维前提(已写入文档):workflow 直接 push 到 `main`,若 `main` 有分支保护需允许 GitHub Actions 绕过。
- 文档:新增 `RELEASING.md`(英)+ `RELEASING.zh-CN.md`(中),沿用项目已有的 `*.zh-CN.md` 约定;修正 `CONTRIBUTING.md` 中已过时的发布说明并链到新文档;`README.md` / `README.zh-CN.md` 各加「贡献」入口。

## 澄清「fetch-depth: 0」与「必须有 changeset」的关系(并修正文档措辞)

- 用户读发布文档后提问:既然已经拉了全量 commit 历史,为什么还必须有 changeset?——说明原文把两步并列,读起来像有因果关系。
- 源码级结论(两者**互不相干**):
  - `fetch-depth: 0` **只服务于 CHANGELOG 署名**。`changeset version` → `applyReleasePlan` → `getCommitsThatAddChangesets` → `@changesets/git` 的 `getCommitsThatAddFiles`,对每个 changeset 文件跑 `git log --diff-filter=AC --follow --max-count=1 --pretty=format:%H:%p .changeset/<id>.md`,把结果写进 `changeset.commit`。
  - 默认 changelog 生成器是 `@changesets/cli/changelog`,实际 re-export `@changesets/changelog-git`,渲染为 `- <sha 前 7 位>: <summary>`。
  - 浅克隆下边界 commit 在 git 眼里没有父提交(`%p` 为空),该文件会进入 `commitsWithMissingParents`,代码检测到 `isRepoShallow` 后循环 `git fetch --deepen=50` 直到找到父提交;非浅克隆则直接兜底写入 SHA。所以 `fetch-depth: 0` 是省掉这层循环/失败。
  - 而「必须有 changeset」是**发布决策**问题:历史无法说明 bump 级别、无法提供面向用户的文案、无法区分哪些提交不该发版、也无法划分「上次发布到哪里」。判断由人在 PR 里给出,changeset 文件是记录载体。
  - 顺带:即使去掉 guard,`changeset version` 在无待发布 changeset 时本身也会 `ExitError(1)`;guard 只是把「晚失败/难懂」变成「早失败/清晰」。
- 文档改动:`RELEASING.md` / `RELEASING.zh-CN.md` 的「workflow 具体做了什么」第 1 步改为说明 `fetch-depth: 0` 的真实用途(含具体 git 命令与浅克隆退化为 `--deepen=50` 循环),并在列表后新增一段引用块「为什么不直接从 commit 历史推导发布内容?」,明确两步无关、以及 workflow 只能发现「一个待发布 changeset 都没有」。
- 验证:`pnpm lint` 干净(99 文件)。
