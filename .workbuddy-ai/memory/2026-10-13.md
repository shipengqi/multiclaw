### 独立核实过的新发现（可直接开工）

1. **C1 / 我独立也发现：`applyTaskPlan` 在 backend/fullstack 预设下是死代码。**
   `Orchestrator.ts:118` 守卫 `i === 0 && stage.some(a => a.id === "architect")`，
   但 `init.ts:10,25` 的 backend/fullstack 是 `product-manager → architect`，architect 落在
   stage 1 → 条件不成立 → title/scope/plan/dependsOn 全丢。现有测试
   （`Orchestrator.run.test.ts:171`）只覆盖 architect 在 stage 0，故未卡住。
   **修法**：把"第 0 个 stage"改成"首次遇到含 architect 的 stage 之后"（`planApplied` 标志），
   并考虑 architectId 不再硬编码。成本 S。
   ⚠️ PM 的能力盘点表把这一项标成"已具备"，是过度乐观 —— 以架构师结论为准。

2. **C2：usage/cost/tool 事件在 `AgentRunner.ts:89-104` 被丢弃。**
   `AcpRuntime.ts:625-626` 已算出 `usage`/`costUsd`（`AgentOutput` 有字段，`types/runtime.ts:105-117`），
   但 `AgentResult`（`types/agent.ts:64-74`）无对应字段 → 成本/用量/工具活动全不可见。
   多 provider 的核心卖点就是成本差异，看不见=卖点失效。修法：`AgentResult` 加**可选** usage/costUsd
   + `OrchestratorResult` 汇总（符合"新字段优先挂结果"约定）。成本 M。

3. **C3：`modelSelection: "arg"` 是死枚举。** `catalog.ts:16` 声明三态，但四个 provider 全是
   `"config-option"`，`AcpRuntime.ts:585` 只处理 `"config-option"`，capabilities 却按 `!== "none"`
   报 `models: true`。RFC §6.4 规划过该值 → 扩展路径上的坑。建议 v1 先收窄类型为
   `"config-option" | "none"`。成本 S。

4. **C4：model 配置错误告警写裸 stderr**（`AcpRuntime.ts:591-593`），TUI alternate screen 下
   用户永远看不到。建议给 `AgentTask` 加可选 `onWarning` 回调（入参类型加可选字段不破坏），
   `AgentRunner` 接到 `orchestration:warning`。成本 S。

5. **C5：`AgentStatus`（`types/agent.ts:62`）无 `cancelled`** → Ctrl-C 后每个 agent 都显示 ✗ failed，
   与真失败混淆。加枚举值会**编译期强制**补 `theme.ts` 的 `STATUS` 表（仓内唯一消费者）。

6. **§3.3：agent 之间无产物传递。** `ContextManager` 只被写 conversation/pipelineAgents/
   availableAgents 三类键（`Orchestrator.ts:37,57,228`），**从不写 agent 产出** → 下游只能靠共享
   文件系统自己重新发现上游成果。与 leader 的 `history`（跨轮）形成不对称。修法：stage 完成后把
   成功 agent 的 output 截断摘要写进 context + 模板加 `{{upstreamOutputs}}`（记得构造时 `set(key,"")` 兜底）。

7. **我额外发现（两位成员都漏了）：`init` 的逐 agent 覆盖含 ★ Leader，但生成的配置里没有

   与 P1-4（init 不写 leader）同源，应一起修。

### 本轮核查查实的关键事实（写给未来的自己）

- **成本可用性（从 bridge dist 源码查实，非猜测）**：
  - `claude-agent-acp@0.89.1` → `dist/acp-agent.js:4428-4445` 发
    `usage_update { used, size, cost: { amount: total_cost_usd, currency: "USD" } }` —— **有真实 USD 成本**。
  - `codex-acp@2.2.2` → `dist/index.js:31936-31939` 只发 `usage_update { used, size }`，**无 cost**
    （另有 `rateLimits` 通道，非 USD 计价）。
  - ⚠️ ACP 的 `usage_update` **没有 input/output token 分项**，只有 `used`/`size`（上下文占用/窗口）。
    所以 TUI 文案应是 `ctx 45.2k/200k · $0.42`，**不是**评审文档里举例的 `12.3k tok`。
- **`AgentDefinition` 加可选 `role?: "planner"`** 是向后兼容的（结构类型加宽入参不破坏调用方）；
  `Orchestrator` 判定用 `role === "planner" || id === "architect"` 兜底，现有 preset 零改动。
- **超时双层同值是真缺陷**：`AgentRunner.ts:55-128` 外层 `withTimeout` 包住整段 `withRetry`（总预算），
  `AcpRuntime.ts:307-314` 内层 `setTimeout` 用 `task.timeout`（单次预算）—— **同一个值**。
  `retries: 0` 时冗余无害；`retries > 0` 时第一次尝试就耗光总预算，**重试永远没机会**。
- **`session/load` 要求 `init.agentCapabilities.loadSession === true`**（`AcpRuntime.ts:543`），
  且刻意**不 fallback** 到新会话（调用方会误以为续上了）。session 复用建议**只服务续跑**，
  不默认跨 turn，避免"同一 agent 跨需求串味"。

### 本次额外修掉的一个真 bug（工程师发现，QA 证实）
`init` 的 override 注入正则把**已有参数的**调用包成双花括号，产出**非法 TS**：

### 两条值得记住的设计结论
- **TeamRow / StreamPanel 不能用中间 `flexShrink={1}` Box**：在 3 子节点的 `space-between` 行里

### 落地的契约（重要，后续改动别破坏）

- **`AgentResult` 新增可选 `model` / `usage` / `costUsd`**；`OrchestratorResult` 新增可选 `totalCostUsd`。
  **不变量：`totalCostUsd` 只在至少一个 agent 上报了成本时存在；无人上报 → 字段缺席（不是 0）。**
  「没有数据」≠「免费」。QA 还实测了最强边界：a 显式报 `costUsd: 0`、b 不报 → 结果是 `0` 且键存在。
- **ACP 只有 `contextTokens` / `contextSize` / `costUsd` 三项可得**（`usage_update` 无 input/output
  token 分项）。所以 TUI 显示的是 `ctx 45.2k/200k · $0.42`，**不要**写成 `12.3k tok`。
- **`AgentTask.onWarning?: (message: string) => void`** —— runtime 的诊断走它；**无回调时回退
  `process.stderr.write`，且历史前缀 `[multiclaw] Warning: ` 逐字节不变**（向后兼容已实测）。
  `AgentRunner` 接到 `orchestration:warning`，message 前缀 `[${agent.name}] `。
- **`agent:output` payload 加宽 `kind?: "text" | "tool" | "tool-detail"`，缺省 === `"text"`**
  （向后兼容关键点，已实测）。**没有新增事件类型**（符合"新结果字段优先挂 OrchestratorResult"约定）。
  `ConsoleReporter` 与 `FileLogWriter` 都**跳过非 text**，所以 **headless stdout 与日志文件逐字节不变**
  （QA 自写对比实测）。日志的定位是「散文转录」，工具活动只服务屏幕。
- **`AgentStatus` 新增 `"cancelled"`**：`AgentRunner` 的 catch 用 `isAbortError` 区分；
  事件类型仍发 `agent:failed`（payload 里的 status 说明是取消）。`theme.ts` 的 `STATUS` 用
  **`■` muted**（**不要用 `⊘`，那是 `skipped`**）；`state.ts` 的 `SETTLED` 必须含 `cancelled`，
  否则 `progress()` 不算它完成、轮次永远停 N-1/N。
- **`Orchestrator.getModel` 已统一为 `resolveModel(agent, config)`** —— 修掉了与 `AgentRunner`
  两份解析实现的不一致（此前 tier-only 配置在 TUI 管线栏显示不出模型）。
- **`ModelSelectionMode` 收窄为 `"config-option" | "none"`**（删掉死枚举 `"arg"`）。catalog 里留了注释：
  重新引入 `"arg"` 必须同时在 `AcpRuntime` 实现分支。`"arg"` 仅存于历史 RFC `docs/rfcs/0001-*.md`（不算违规）。
- **`verbose` 是 console 态（挂 `TuiState`，不是 `TurnView`）**，所以 `snapshot()` 不写进历史；
  `turn:start` 要显式保留它。`/verbose` 控制 `tool-detail` 是否进流（`tool` 摘要行默认就显示）。
- **`TuiState` 新增字段时别忘了 `snapshot()` 是逐字段写出的**（`totalCostUsd` 已补）。

- `claude-agent-acp@0.89.1` → `dist/acp-agent.js:1404`（`loadSession()` 实现在 `:1511`，注册于
  `methods.agent.session.load` `:9067`）

### 落地的契约（后续改动别破坏）

- **`AgentResult.sessionId?: string`**；**`OrchestratorResult.requirement?: string`**。
  `requirement` 是必需的：`report.json` 就是 `orchestration:complete` 的 payload，而 requirement 此前
  只在 `orchestration:start` 里出现过 → 不补它，`--resume` **读不到原始需求**。
- **`MultiClawConfig.resume?: { agents: string[]; sessions?: Record<string, string> }`** —— 沿用
  `history` 的先例：会话状态由调用方带入，core 无 session 概念。**设了 `resume` 就跳过 leader**
  （否则会重新路由、可能选出与正在续跑的不同的团队）。
- **`Orchestrator.resolveTurn` 的 resume 分支复用 `selectAgents`**（不另写筛选）：未知 id 告警、
  `agent:skipped` 发射、**`dependsOn` 裁剪**（单 agent retry 的依赖正好因此被清空 —— 否则
  `buildStages` 会因缺依赖抛错并降级成 declaration order）。
- **`selectAgents(run, namedBy = "The leader")`** —— 加了来源标签。resume 运行**没有 leader**，
  传 `"The resume list"`，否则用户会看到指向不存在对象的告警。默认参数 → 既有调用点零改动。
- **`AgentTask.sessionId` 缺省必须是 `undefined`，不是 `""`**（`AcpRuntime` 用 `if (task.sessionId)` 判定）。
- **`--resume` 绝不覆盖原 `report.json`**：`workDir` 指回原 run 目录（**cwd 必须一致**，否则
  `session/load` 的会话指纹变化会让桥**重建**会话而非加载），日志写 `<runDir>/logs-resume-<stamp>`。
- **`/retry [id]` 作用于 `state`（最后一轮），不是 `shown`**（回看旧轮次时重试会拿错 requirement/agents）；
  `availability: "idle"`；无参数只收 `status === "failed"`；`sessions` 无人有 sessionId 时**省略键**。

### 刻意裁剪：只在成功路径捕获 `sessionId`（如实记录为降级）

ACP 只在**完成的 turn** 上回传 session id（`AcpRuntime.ts:649` 在 `settleResolve` 里），失败路径拿不到。
**不给失败路径新造通道**，理由：① 需加宽已发布的 `RuntimeEvent` union；② 一个死掉的 turn 未必有可复用的
持久会话，硬续可能让「重试」因 `session/load` 失败而更糟。**代价**：`/retry <失败 agent>` 冷启动；
续跑真正省下的是**已成功** agent 的重复探索。`AcpRuntime` 本批**未改动**。

### QA 的两处关键判定

1. **「不设 `resume` 时行为不变」成立**，但表述要精确：**routing 行为不变 + 结果新增 additive 可选字段**
   （`sessionId` / `requirement`，缺值时字段缺席）。当 `context.requirement` 有值时 `report.json` 会多一个
   `requirement` 字段 —— **不是字面「逐字节一致」**。QA 的证伪方法值得记：把守卫临时改成 `false &&`
   （resume 用例全红、非 resume 用例全绿 → 证明守卫是唯一开关）＋ 键集合与**键顺序**精确断言
   （`requirement` 追加在末尾，不移动既有键，所以 `JSON.stringify` 的字节序不变）。
2. **推翻了工程师的一处理由**：`run.ts` 的 0% 覆盖不能拿「`index.ts`/`lib.ts` 被排除」当借口 ——
   被排除的**只有那两个**，`run.ts` 是被计量的。补了 `run.test.ts`（`vi.mock` 掉
   loadConfig/Orchestrator/reporters/lib，真跑 `runCommand`）→ run.ts 行覆盖 0%→88%，
   cli 总计 `68.51→76.07`。**这是比抽纯函数更强的做法：断言落在真实代码路径上。**

### 一个可复用的测试模式（值得沿用）

`run.test.ts` 用 **`vi.hoisted` + `vi.mock` 工厂共享可变状态**（`vi.mock` 会被提升到 import 之上，
普通 `let` 读不到），让被 mock 的类把构造参数（`config`、`logDir`）记进共享 state，测试再断言。
用于测「命令入口把什么交给了依赖」这类接线不变量，比抽纯函数更贴近真实路径。

### 落地的契约（后续改动别破坏）

- **`packages/core/src/utils/upstream.ts`（新）**：`renderUpstreamOutputs(outputs)` → 渲染块或 `""`。
  `MAX_UPSTREAM_ENTRY_CHARS = 600`（单条 entry）、`MAX_UPSTREAM_CHARS = 4000`（整个 block）。
- **两个上限都必须含自己的框架 —— 这是 F1 与 F4 两次踩的同一个坑**：
  - block 预算含 `HEADER`(`\n## What upstream produced\n\n`) + `TRAILER`(`\n`)。F1：原实现只量
    `entries.join("\n")`，返回串可达 4028 > 4000。
  - entry 预算含归属行 `- name (id):\n  ` + **每换行 2 空格的续行缩进**。F4：原实现先
    `compact(body, 600)` 再缩进，多行 entry 可达 892。
  - **判据：文档承诺的是「渲染后的产物」，就量渲染后的产物**，不要量中间量。
- **`compact(text, max)`**：head+tail 保留 + marker 报**真实**省略字符数；确定性、同步、**非 LLM 摘要**
  （作者决策②：不做硬截断，也不做模型摘要）。`compact` 保证返回长度 ≤ `max`
  （`keep = max − reserved`，且 marker 用实际位数 ≤ reserved）。
  - **退化路径**（`budget − 2N < reserved` ⇒ `keep = 0`）：body 塌缩为 marker，重算**有意是 no-op**；
    此时 entry 上界是 `label.length + markerLen` 而非常量（需 name+agentId ≈ 562 字符才越界，
    现实不可达）。**不要为这个角落去截断 agent 名**，也别把注释改回「无条件成立」。
- `renderUpstreamOutputs([])` 返回 `""`（与 `renderConversation` 一致）；模板把占位符**独占一行**，
  空值时只留一个无害空行、不留悬空标题。
- `Orchestrator` 构造里 `set("upstreamOutputs", "")` 兜底；**每个 stage 结束后**把**成功** agent 的产出
  写进 context；11 个 preset 模板加 `{{upstreamOutputs}}`（leader 除外）。
- dashboard：`GLYPH.newline = "↵"`；`App.insert` 把 `\r\n?` 归一化成 `\n`；`Prompt` 把 `\n` 渲染成 `↵`
  —— **必须严格 1:1 替换**，caret 的字符索引算术才不用改。`\r` 的清理是**防御性且非 1:1**，
  前提（`\r` 到不了 `line.text`）由调用方 `App.insert` 保证。

### 环境坑（本机沙箱，与代码无关）

`pnpm test:coverage` 在**本机沙箱**会以 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` 失败：
vitest 的 `V8CoverageProvider.cleanAfterRun`（`coverage.DM_a_rWm.js:774`）要删
`packages/*/coverage/.tmp`（约 54-58 个文件），被批量删除保护拦下（阈值 50）。
**这是报告完成之后的清理步骤，不是覆盖率不达标**，覆盖率表格正常打印。CI 无此 shim，不受影响。
`--coverage.cleanAfterRun=false` 与 `--coverage.reportsDirectory=<外部路径>` **都会被 vitest 忽略**
（拿不到干净退出码）。`pnpm verify` 只跑 lint+build+typecheck+test，**不查覆盖率门槛**。
